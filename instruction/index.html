Authoring maintainer tasks

Every task is a change you would approve as this project's maintainer: you pick a realistic feature or fix on a large private codebase, write the request for it, produce the change you would genuinely accept, and write the grading criteria that decide whether another change would be approved too. Approved tasks pay $75 each. Read this page fully before your first task.

What a maintainer task is

A candidate change is graded the way a maintainer reviews a contribution. Blockers are the reasons a maintainer would turn it down: the requested behavior is broken, a case the request clearly implies is missed, existing tests or callers break, the change touches what it must not. A change is solved only when every blocker passes. Non-blockers are weighted criteria (readability, fit with the codebase, test quality, how focused the change is) that never fail it. A solved change's score is the weighted mean of every criterion, blockers included; a change that fails any blocker scores 0.

  1. Claim a repository from the shared pool, or connect a large private repository you own.
  2. Author the task: the prompt, the golden patch, the hidden tests, the grading criteria and two calibration patches.
  3. Verification and review: the platform runs automated checks, then a reviewer works through a checklist.

Claim or connect a repository

Tasks are written on large private repositories in a shared pool. Browse the pool on the Repositories page and claim the one you will work on; a pool repository has nothing to upload or connect. Claims are limited, so claim only what you intend to author against, and release a claim you no longer need. Each pool repository comes with a published environment pinned to a base commit.

You can also connect a large private repository you own from the same page, under "Connect a private repository". It goes through the same connect checks as any repository, you author on it directly, and it joins the pool for other experts under the same sharing rules.

If you connect your own, a good fit is an actively maintained library, SDK or framework with roughly 20,000 or more lines of source, a public API, an existing test suite that passes, and lint and type checks already set up. Smaller codebases rarely leave room for the sibling-path and compatibility cases that good tasks need. This is a recommendation, not a requirement.

  • Keep the code and every task file private under the sharing terms you agreed to.
  • Read the codebase before you write anything. You need maintainer-level judgment of what this project would and would not accept.
  • Never paste the code, or the change, anywhere public.

Pick a realistic change

  • A real change, not a planted bug. A genuine feature or a genuine defect fix this project would take on. Never inject a bug into clean code to be undone.
  • Hard for the right reason. The difficulty must come from the engineering: a non-obvious root cause, a subtle interaction, an architectural constraint, the cases a careful maintainer would also cover. Never from a broken environment, a flaky test or a confusing prompt.
  • Pull-request sized. A real change usually reaches across several files: the fix or feature, the code paths beside it, and its tests. Prefer a task of that size over a one-line fix.
  • Something you would accept. If you would not approve the golden patch into this repository, it is not a valid task.

Task types

Every task has a type, picked when you create it (or at the top of the workspace for a draft that has none); submitting refuses a task without one. Aim for a spread across the types over your tasks, not only bug fixes.

FeatureNew functionality. Hidden tests cover the behavior through public interfaces, plus the inputs and modes the neighbouring code already supports.
Bug fixA defect in existing behavior. Hidden tests reproduce it, and cover the same defect wherever else it shows up.
SecurityA vulnerability closed. Hidden tests exercise the exploit path (the crafted input, the bypass, the injection) and confirm it is closed, and other tests confirm legitimate use still works the same, so a change that blocks everything cannot pass.
PerformanceFaster or leaner. Its blockers must be deterministic: a relative speedup against the unchanged code, or a complexity bound (operations, allocations, queries) on fixed-size inputs, with generous margins and inside the verifier time limit. Never a wall-clock threshold, which varies by machine and makes the task flaky. Correctness tests stay blockers too.
RefactorA restructure the project wants. Behavior and public interfaces stay the same: pass-to-pass tests and compatibility blockers carry most of the weight, with hidden tests for the new structure where it is observable.

Write the prompt

instruction.md is what the solver reads: your task description, then the repository's codebase guidelines, then a closing line about the base commit. No heading separates the two parts. You write only the description; submitting puts the guidelines and the closing line after it.

Task descriptionAn informal request at the top of the file, the way a user files an issue or a colleague asks for a feature: the goal or the symptom, why it matters, and any real constraint, in your own words. State the goal, not the approach, and do not spell out what a maintainer would infer from the request and the code (the same bug in a sibling code path, the input types the neighbouring code already supports, cleanup, keeping public interfaces working): your hidden tests check those. Name only what nobody could infer: a new public name, command or output format your hidden tests rely on. Never dictate private helpers, files to edit or the algorithm, and never include pseudocode. Keep it to 60–300 words, not counting the codebase guidelines after it; the submit check refuses a description outside that range. Write it the way a person asks: no upload preamble or task wrapper, and no mention of how the change is checked (a verifier, grader, rubric, criteria, score, reward or hidden tests).
Codebase guidelinesFree-form text written once per repository and carried by every task on it, after the description: whatever a contributor needs to know about how changes are made there. Most repositories want test guidelines (how to run and write tests), lint guidelines (the linters and formatters to run) and style guidelines (the conventions a pull request is held to); add or drop sections to fit the repository. It describes the repository, never this task. The first task on a repository starts from a draft made from the repository's own tooling and docs: check and correct every line in the task's guidelines box, because when that task passes the submit checks, that text becomes the repository's version 1. Every later task carries the current version unchanged. To change it, use "Suggest a guidelines edit" on your task: the suggestion goes with the task and never holds it up, and the repository moves to it only if it is applied. The quality check reads the guidelines against the repository: the commands must exist, the conventions must match the code. Aim for about 1,000 characters; the check warns above 2,000.

No links to issues, pull requests or upstream discussions, no issue numbers, no commit hashes. Two example task descriptions in the right register, a feature request and a bug report:

Exports for large workspaces keep timing out, and when one fails halfway the user gets a partial CSV with no warning that rows are missing. Support has seen this three times this week.

Could you make exports stream instead of building the whole file in memory, and make sure a failed export never hands the user a truncated file? If an export cannot finish, the user should see that it failed and be able to retry it. Small exports should behave exactly as they do today, including the column order and the header row.
Since the last release, retrying a failed upload from the queue page sometimes sends the file twice, and the second copy shows up as a separate item in the workspace. It only seems to happen when the first attempt timed out rather than failed outright. Could you make retries safe? A retried upload should end up as one item, whatever happened to the first attempt.

The task files

instruction.mdThe prompt: your task description, then the codebase guidelines and the closing line (added on submit).
environment/repo/Provided by the platform at run time, at the base commit. Leave it out of your task files.
solution/patch.diffYour golden patch: the change you would approve.
solution/alternative.patchA different but valid solution. Must pass every blocker.
solution/negative.patchA plausible wrong solution. Must fail a blocker or score below the quality threshold.
tests/hidden/Hidden tests and the criteria runner. Never visible to the solver. At least 2 test files and 430 non-blank lines.
tests/grader/grader.yamlThe mechanical criteria (tests, commands, scope) with method, blocker, weight and rationale for each, and the calibrations.
tests/grader/rubric.tomlThe judged criteria: yes/no questions a judge answers from the diff, each with a weight and an optional blocker flag.
tests/test.shRuns every criterion and writes the result.
task.tomlThe task's settings. Fill in displaytitle and displaydescription. [agent] timeout_sec is the time each automated attempt gets: anywhere from 7,200 to 28,800 seconds (2 to 8 hours), and a new task starts at 7,200. Give it the time a strong engineer new to the codebase would need, with room to spare; the submit check refuses a value outside that range. Set it here on the task page (the build kit keeps the task page's value). Leave every other value as it is.

The golden patch

solution/patch.diff is your golden patch: your own solution, with the unit tests that prove it works, as git diff against the base commit. It must apply cleanly and pass every blocker. Make it thorough: fix every instance of the problem, not only the one the request names. The submit check requires at least 450 added lines across at least 4 files, and between 0.9 and 7.5 added lines per word of the task description. A golden patch over 3,000 changed lines or 60 files gets a warning: it is allowed, but check that it is one pull request and not several. One under 50 changed lines, or touching a single file, gets a soft warning: tasks here are real pull requests that usually reach across several files.

Grading criteria

The grading lives in two files. tests/grader/grader.yaml holds the checks a machine decides: each criterion has a method (classical, command, reverse_classical or scope), a blocker flag, a weight and a one-line rationale. tests/grader/rubric.toml holds the questions only a reader can judge (see Judged criteria below). Use a deterministic check wherever one can decide the question.

The platform adds three checks from your repository's toolchain: the full test suite (regression_safety), build, type check, format and lint (mechanical_cleanliness) and that new tests fail before the change (test_correctness); you can change blocker and weight.

Fail-to-pass (f2p) tests, a blockerHidden tests that fail on the base commit and pass with a correct change (the f2p criterion in grader.yaml). Test behavior through public interfaces, never grep source for names. List each test by id in the criterion's tests (with the report its command writes): the submit check requires at least 10 named tests here, and a criterion with no tests names none.
Pass-to-pass (p2p) tests, a blockerExisting tests the change must not break (the p2p criterion). They must pass both before and after your golden patch. List each test by id in the criterion's tests (with the report its command writes): the submit check requires at least 50 named tests here, and a criterion with no tests names none.
Protected surfaces (scope), a blockerThe protected_surfaces criterion: denied_paths naming what the change must not touch (public API modules, generated files, persisted formats, unrelated subsystems, legacy modules the project keeps unchanged), with every other path allowed. Submit adds a loose size cap (ten times your golden patch) that only a wholesale rewrite trips. Keep any counts on a blocker that loose; a tighter one gets a warning, because a reasonable broader fix would fail the task.
Focused change (scope), a non-blockerThe focused_change criterion, with a small weight: allowed_paths covering the implementation area AND its tests, and the file and line counts a reviewer would expect. Submit fills generous counts from your golden patch (its files plus three, three times its lines) once; change or remove them as you see fit. Missing it lowers the score, never fails the task. Never tripped by a formatter run.
Thoroughness and compatibility, blockersHidden tests for what a maintainer would expect from the request even though it does not say so, and for keeping public interfaces and stored data working. See the next section.
Judged criteria (rubric.toml)5 to 15 yes/no questions specific to this task, each one a reader can answer from the diff; a question can be a blocker. See Judged criteria below.
Solver testsIf the prompt asks for tests, a criterion runs them against the base commit and requires them to fail there.

What is a blocker. Mark a criterion as a blocker only where a maintainer would turn the change down over that failure alone. Style, naming, structure preferences and other matters of taste are non-blockers. When in doubt, make it a non-blocker.

Every blocker must be something a careful engineer could infer from the prompt, the codebase guidelines, the codebase itself or what any maintainer of this code expects. A blocker that needs an exact name, format or message only you know is unfair and will be sent back.

You may tag a criterion with an optional blocker_category naming the kind of merge-stopper it guards against: thoroughness, core_behavior, regressions, test_writing, lint_format_typecheck, scope, backwards_compat, compilation, test_integrity, docs_metadata or implementation_detail. It is never graded.

Judged criteria

tests/grader/rubric.toml holds 5 to 15 yes/no questions that only a reader can decide: what a reviewer of this change would actually look for, not generic advice. Write one [[criterion]] table per question, below the [judge] table (that table is the platform's and is rewritten on submit):

  • description: the question, answerable yes or no from the diff, naming the file or directory it judges.
  • type = "binary": the judge asks each question once and answers yes (1) or no (0). No other type is supported.
  • weight: a positive number, its share of the score.
  • Optional: an id (letters, digits, _ and -), and a [criterion.annotations] table with blocker = true when a maintainer would refuse the change over a "no" alone. A judged blocker answered no makes the attempt score 0, like a blocker in grader.yaml.

The score is the weighted mean of every criterion in both files (each counts 1 when it passes and 0 when it fails), and 0 when any blocker in either file fails. Use a deterministic check in grader.yaml wherever one can decide the question.

The automated review checks every question against these rules, and a task that breaks one is sent back to you (that is the review blocking the task, not a solver failing it):

AtomicEach question checks one thing. "Does the parser in src/parse.ts reject empty input and keep the error type?" is two questions; split it.
UnambiguousMaintainers of this repository voting on any change would reach a clear majority. "Is the code in src/cache/ clean?" depends on taste; "Does src/cache/store.ts release the lock on every early return?" does not.
Not fitted to your patchAnother correct solution passes every question. Ask about the behavior or property, never about the helper, name or structure your golden patch happens to use.
Blockers are merge-stoppersMark a question a blocker only when a maintainer would refuse the change over a "no" alone. Readability and fit with the codebase stay non-blockers.
InferableAn experienced engineer could work out every question from the description, the guidelines and the code. A question about a detail only you know is unfair.
Weighted by importanceWeights follow how much each question matters compared to the others: a question about correctness weighs more than one about a docstring.
ComprehensiveEvery requirement in the description is checked by at least one criterion in either file. A requirement a hidden test already checks needs no question too.

Thoroughness and compatibility blockers

Requests leave things out. A good contribution still gets right what a maintainer can infer from the request and the existing code, and that is the most common reason a plausible change is turned down. Write hidden tests for that inferable but unstated behavior, and make the criteria that run them blockers:

  • Fix every instance. The request reports a bug in one code path, and the same bug sits in a sibling path (a second caller, the async variant, the other platform). Test both.
  • Match existing support. The request asks for a feature and mentions one input type, while the neighbouring code handles others (another file format, a second kind of handler, both sync and async callers). Test the ones a maintainer would expect to work too.
  • Cleanup and resources. When the change discards something the user created, it must release it the way the language expects: a generator that is dropped is closed so its finally block runs, a stream or handle is closed, a subscription is cancelled, partial work is rolled back on failure. Test that the cleanup happens.
  • Backwards compatibility. When the change touches a public interface (an exported class or function, a module path callers import, a flag, a configuration key, a route) or a format already written to disk or the wire, existing callers and existing data must keep working unless the request asks for the break. Removing or renaming a public class to fix an internal bug is a breaking change. Protect it with pass-to-pass tests on the public surface, a test that reads the old format, or denied_paths on the protected module.

Keep these to what a maintainer would really expect. A test for an exact message, a new name or a format nothing implies is not thoroughness; it is an unfair blocker.

Calibration patches

  • solution/alternative.patch is a correct solution shaped differently from your golden patch. It must pass every blocker. If it fails one, your criteria are fitted to your own implementation.
  • solution/negative.patch is a plausible wrong solution: a shortcut, a hard-coded output, a change that skips a case. It must fail a blocker or score below the quality threshold (a score under 0.5). If it passes, a wrong change could too.
  • Your golden patch must earn close to full credit on your own judged criteria: on every reference run its weighted score on rubric.toml must be at least 0.9, so it gets a yes on nearly every question. If it does not, the questions do not describe the change you would merge.
  • Try to break your own grader before you submit. Anything wrong that passes will fail review.

Work locally with the build kit

The Build kit tab has maintkit, a command-line kit for writing a task on your own machine. It needs Node.js 20 or newer. Patch applicability requires Git history, and verify also needs Docker. Its structural checks are built into each release. A local PASS does not guarantee submission or reference verification will pass. The task page also supports drafting and structural checks.

  1. Install: download the full kit from the Build kit tab, unzip it, and run ./maintkit rules in the build-kit folder. When a new release lands, download the update and run its apply.sh over your kit; your tasks/ folder is never touched.
  2. init: create the task here first (New task), then run maintkit init tasks/<name> --base <commit> with the same task name and the task's base commit (the base_commit line of its tests/grader/grader.yaml). It scaffolds exactly the files the workspace starts with. Write only the description in instruction.md: the codebase guidelines are added on submit.
  3. check: maintkit check tasks/<name> checks structure without applying patches or running tests. Add --repo <working copy> only when you have a real Git working copy containing the exact pinned base commit; it then checks each patch against that commit.
  4. verify: maintkit verify tasks/<name> --repo <working copy> --dockerfile <environment Dockerfile> requires a real Git working copy containing the exact pinned base and the approved Dockerfile for that environment version. It builds locally without pulling the private platform image and grades the golden, no-change, negative and alternative patches with the expectations calibration holds them to. The judged criteria in rubric.toml need a judge: set MAINTKIT_JUDGE_BASE_URL, MAINTKIT_JUDGE_KEY and MAINTKIT_JUDGE_MODEL to your own chat-completions endpoint, or they are left out and the run says which results it could not decide. A local result is a preview; the platform runs its own calibration after you submit.
  5. pack: maintkit pack tasks/<name> runs structural checks and writes a draft zip. It does not prove patch applicability or execute the verifier.
  6. Upload: drop the zip on the task page, or add it on New task. It replaces the description, the three patches, grader.yaml, the criteria in rubric.toml and the hidden tests; the generated files stay. A zip packed with an older kit says so.

A borrowed connected-repository ZIP is a source snapshot without Git history; its approved environment Dockerfile may also be unavailable. Use check and pack without --repo for structural checks and draft packaging only. Full local verification is currently unavailable from that ZIP alone. Keep the original pinned base unchanged. Private-registry login does not fix this limitation; report the missing local inputs instead of submitting to debug them.

What happens after you submit

  1. Automated checks: The files, the prompt length and its two parts, links and references, the grading criteria counts, both calibration patches present.
  2. AI check: The prompt must be your own prose, not generated.
  3. Originality: The task must not be a near copy of an earlier one.
  4. Reference verification: Your golden patch must pass every blocker; the unchanged repository must fail; the alternative patch must pass and the negative patch must fail.
  5. Quality review: Automated review of the full bundle: prompt clarity, grading criteria that follow from the prompt and the codebase, verifier integrity.
  6. Adversarial review: An automated attempt given only your prompt and the repository tries to earn credit from your grading without doing the work.
  7. Calibration I: Automated attempts confirm the task is not too easy.
  8. Calibration II: Automated attempts confirm the task sits inside the target difficulty range; an attempt that looks the solution up online does not count.
  9. Run audit: Unsuccessful attempts are audited: an environment defect fails the task, genuine difficulty passes.

Then human review: a reviewer works through the checklist, then an admin gives final approval.

A failed stage shows what failed and why on the task page. Revise and resubmit.

Review and payment

One reviewer works through a fixed checklist: the change is realistic, the prompt is fair, wrong solutions fail, every blocker is a true merge-stopper, scope is not brittle, the task is hard for the right reasons, and nothing hidden leaks to the solver. Any failed item sends the task back with a reason. A task the reviewer passes goes to an admin for final approval. Approved tasks pay $75 each.

Common pitfalls

  • The description names the function or file to change, or narrates the patch.
  • The description spells out every case the tests check, so nothing is left to infer.
  • The blockers check only the literal ask: the sibling code path, the other input types or the cleanup go untested.
  • A blocking scope rule with tight file or line counts that a correct, slightly broader fix would trip.
  • The codebase guidelines hint at this task, or are generic advice the repository does not follow.
  • A blocker checks style or taste.
  • A blocker asks for something the prompt, the guidelines and the code never imply.
  • A pass-to-pass test already fails on the base commit.
  • The alternative patch fails a blocker, or the negative patch passes.
  • Code-quality criteria that would fit any task.
  • A judged question that checks several things at once, or that maintainers could answer either way.
  • The golden patch or hidden tests are reachable from the repository the solver sees.
