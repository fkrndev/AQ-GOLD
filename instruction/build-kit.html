Working with the kit

Create the task here first (New task) and note its base commit, write it in the kit, then drop the zip on the task page. For a borrowed source ZIP, run check and pack without --repo for structural checks only. Full local verification is unavailable from that ZIP alone. The kit's README is the full reference.

maintkit init tasks/<name> --base <commit>
Scaffold a task folder the way New task does: the description, the three patches, the grading criteria, hidden tests and the verifier frame. Use the task's base commit (its grader.yaml shows it).
maintkit check tasks/<name>
Structural checks on your files, offline, without executing tests: the description, the grading criteria and their structure, the size and test-count minimums, scope, the calibrations, and that each patch is a clean diff.
maintkit verify tasks/<name> --repo <working copy> --dockerfile <environment Dockerfile>
Requires a real Git working copy containing the pinned base and the approved environment Dockerfile. Build locally and grade the four patches; a borrowed source ZIP alone cannot support this command.
maintkit pack tasks/<name>
Run structural checks, then package a draft zip for the task page. This does not apply patches or execute the verifier.
maintkit rules
The ranges every check uses. Ranges, not targets.

  • 1.3.0 · Oct 29, 12:33 AM PDT

    What changed in 1.3.0

    Tasks now have to meet minimum sizes and test counts. The submit check already enforces them, and maintkit check now reports them offline with the same messages:

    • Golden patch: at least 450 added lines across at least 4 files in solution/patch.diff.
    • Hidden tests: at least 430 non-blank lines of test code across at least 2 test files under tests/hidden/.
    • Fail-to-pass tests: the f2p criterion lists at least 10 test ids. Fewer than 20 gets a warning.
    • Pass-to-pass tests: the p2p criterion lists at least 100 test ids. If the code next to the change has fewer tests, widen the command to more of the existing suite and list those ids too.
    • Description length for the change: 0.9 to 7.5 added lines of the golden patch per word of the task description.

    The test counts come from the ids you list. The f2p and p2p criteria in tests/grader/grader.yaml each name the test report their command writes (report: /logs/verifier/f2p.xml) and list every test id that must pass in it under tests:. A criterion with no tests list counts as zero. Use each id exactly as the report names it: JUnit classname.name, or the test's name for ctrf. Every listed id must pass in the report, so verify shows a mistyped id straight away. init now scaffolds both criteria with a report and a tests list, and the README's new "The test criteria" section has a worked example. maintkit rules prints every minimum.

    verify also runs the current verifier. A command that writes its report to a literal /logs/verifier/... path works again. A command that cannot run at all (exit 126 or 127, such as a missing tool) leaves the run ungraded (verify reports INFRA) instead of failing the check.

    Updating from 1.2.0: unzip the update archive and run sh maintkit-build-kit-1.3.0-update/apply.sh <your build-kit folder>. Your tasks/ folder is left alone, and ./maintkit --version prints 1.3.0 afterwards. For each task you have not uploaded yet:

    1. In grader.yaml, give the f2p and p2p commands a JUnit (or ctrf) report, for example --junitxml=/logs/verifier/f2p.xml with pytest, and add the matching report: line.
    2. Run the command once, then copy every test id from the report into the criterion's tests: list.
    3. Run maintkit check. It names any minimum the task does not meet yet. Then run verify and pack before your next upload.

    The update also applies cleanly over 1.0.0 and 1.1.0; a task folder from those releases also needs the changes in their notes.

  • 1.2.0 · Oct 28, 5:16 PM PDT

    What changed in 1.2.0

    • Judged criteria are yes/no questions. Every [[criterion]] in tests/grader/rubric.toml is now type = "binary": the judge asks each question once and answers yes (1) or no (0). points and threshold are gone; check refuses them.
    • A question can be a blocker. Add [criterion.annotations] with blocker = true when a maintainer would refuse the change over a "no" alone. A judged blocker answered no makes the attempt score 0, like a blocker in grader.yaml. The alternative patch must pass every judged blocker too.
    • 5 to 15 questions per task (was 3 to 8). init seeds five placeholders.
    • New review rules for the questions. Each checks one thing, has an answer maintainers would agree on, accepts other correct solutions, is inferable from the description and the code, and is weighted by importance; a blocker question is a real merge-stopper; and every requirement in your description is checked somewhere. The guide's Judged criteria section has an example for each.
    • verify asks the local judge once per question, as the platform does, and prints yes or no for each, marking the blockers.

    Update with sh apply.sh <your build-kit folder>, then convert any rubric.toml written for 1.1.0: change type = "likert" to type = "binary", drop points and threshold, and reword each criterion as a yes/no question. Re-run maintkit check and maintkit pack before your next upload.

  • 1.1.0 · Oct 28, 3:59 PM PDT

    The task layout changed. Bundles packed with 1.0.0 are refused at upload, so update the kit before you pack your next task.

    • Judged criteria live in tests/grader/rubric.toml. Write one [[criterion]] table per question (description, type = "likert", points = 5, weight, an optional [criterion.annotations] threshold, 0.6 by default). Each is scored 1 to 5 and is never a blocker. The platform writes the [judge] table at the top of the file and judge-prompt.md beside it.
    • tests/grader/grader.yaml holds the mechanical checks only: classical, command, reverse_classical and scope, plus the calibrations. llm_prompt is no longer a method. Move those criteria into rubric.toml.
    • Attempt time is 2 to 8 hours. task.toml [agent] timeout_sec must be between 7200 and 28800. New tasks start at 7200, and you set the value on the task page.
    • The criteria runner is no longer a task file. tests/hidden/run_criteria.py is gone: the verifier runtime carries the runner. The kit and the upload ignore an old copy in your folder.
    • verify runs the hardened verifier. Graded commands run as an unprivileged user, with no network and with the test files locked. A command that needs root or the network fails here as it would on the platform. By default the local judge is asked the same number of times per criterion as the platform's judge (MAINTKIT_JUDGE_SAMPLES overrides that), and the patch is copied into the container, so verify works wherever your task folder is.
    • Upgrading a 1.0.0 task folder: apply the update, then run maintkit init on a scratch folder with the same name and base commit and copy its tests/grader/rubric.toml into your task. Rewrite each llm_prompt criterion from grader.yaml as a [[criterion]] table there, delete it from grader.yaml, then check and pack again.

    To update in place, unzip the update archive and run sh apply.sh <path to your build-kit folder>. Your tasks/ folder is left alone.

  • 1.0.0 · Oct 27, 3:18 PM PDT

    First release of the maintainer build kit.

    • maintkit init scaffolds a task folder exactly as New task does.
    • maintkit check runs the submit's checks on your files offline, and with --repo applies each patch to the base commit.
    • maintkit verify builds your environment in Docker at the base commit and grades the golden, no-change, negative and alternative patches with calibration's expectations. Prompt-graded criteria use your own chat-completions endpoint (MAINTKIT_JUDGE_BASE_URL, MAINTKIT_JUDGE_KEY, MAINTKIT_JUDGE_MODEL), or are left out with a note.
    • maintkit pack writes the zip you drop on the task page or add on New task.

    Needs Node.js 20 or newer and git; verify also needs Docker. See README.md in the kit.
